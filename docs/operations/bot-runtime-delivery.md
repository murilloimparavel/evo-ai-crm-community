# Durable Bot Runtime delivery

For incoming messages in active, non-moderated Bot Runtime inboxes, an `after_create` callback inserts a message journal in the same database transaction. The after-commit listener enqueues the journal ID. A scheduled sweep each minute recovers an enqueue failure or worker interruption. The sweep orders due journals by next-attempt time and reserves each page for five minutes in a short SKIP LOCKED transaction before enqueueing. Failed listener evaluations persist bounded backoff outside their rolled-back transaction. Poisoned journals and failed queue delivery therefore rotate behind untouched work instead of monopolizing the oldest 500 records. The worker reuses the existing listener eligibility checks; skipped messages are acknowledged as evaluated. Eligibility is evaluated at processing time, so messages delayed until a human takes over must still respect the conversation gate.

Eligible delegation creates a unique delivery for `(message_id, agent_bot_id)` before enqueueing an ID-only job. It preserves the original delegated text, reconstructs current credentials and fresh attachment URLs at send time, and marks delivery acknowledged only after the runtime accepts it (or an idempotent audio fallback succeeds). It rechecks the current bot assignment and conversation status/label gate immediately before external processing; blocked deliveries are recorded separately as `skipped_at` with a reason, never as sent. Exceptions, including circuit-open, remain pending with bounded exponential backoff; scheduled replay continues after ordinary job retry exhaustion. Runtime must deduplicate stable CRM message IDs before acceptance. A lost HTTP acknowledgement can cause an intentional retry.

Apply the database migration before deploying the application. Existing serialized `SendEventJob` jobs remain supported during a rolling upgrade. The runtime must implement durable acceptance and deduplication before CRM replay is enabled. Disabling Bot Runtime pauses new journal processing and pending delivery; replay resumes on re-enable. Do not use historical conversation replay as an automatic backfill.

Moderated inboxes keep the existing synchronous listener path because moderation may have external side effects that are not proven idempotent. Their eligible delegations still use durable delivery, but their message-to-listener gap is not covered. The non-moderated path resets inactivity actions and rechecks existing pending moderation records; it does not add any message-send side effects before delegation. Session-history sync has its own ledger and is not considered proof of runtime delivery.

Monitor oldest unprocessed journal, oldest pending delivery, attempt counts and last error class. No credentials or complete event payloads are stored in the ledger. Pending rows must never be purged for age alone. Acknowledged journals/deliveries may be removed under the installation's customer-data retention policy only after the runtime deduplication horizon has passed; retain message IDs for at least that horizon. Foreign keys cascade removal when the original message or bot is deleted.

Known limits: message updates remain on their existing listener path and runtime IDs still represent the original message, not a content revision. Moderation, human/bot configuration changes during an outage, and idempotent audio fallback require their existing policies. This change does not create exactly-once external effects. AudioFallbackService already deduplicates the reply against its original incoming message; delivery failures remain pending. Network and transcription operations use a ten-minute attempt lease outside database transactions; expired workers cannot acknowledge a newer attempt.
